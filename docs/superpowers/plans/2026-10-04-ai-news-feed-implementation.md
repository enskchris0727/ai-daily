## 2. 阶段划分

整个实施分 6 个阶段。**每个阶段结束都是一个可检验的节点**，不会出现“全部做完才发现方向不对”。

| 阶段 | 内容 | 产出的可验证结果 |
|---|---|---|
| 1 | 项目骨架 | 目录结构和依赖就位，能跑一个空测试 |
| 2 | 来源实测 | 一张真实的结果表：哪些源能用、各有多少条 |
| 3 | 抓取器 | 能真的把内容抓回来并存成标准格式 |
| 4 | 整理器 | 能生成符合设计的数据文件，有测试保障 |

顺序不是随便排的：**第 2 阶段先做来源实测**，因为“有多少源能稳定抓取”是整件事的地基。万一某类源大面积不可用，我们可以及早调整，而不是等页面都做完了才发现没内容。

## 4. 阶段 2：来源实测（关键阶段）

**目的**：把设计文档第 2 节列出的候选来源，逐个真实验证一遍，得出**最终可用清单**。

这一步是整件事的地基，所以放在最前面。

### 步骤

1. 为每个候选来源准备候选地址（优先级：RSS → 官方 API → 网页解析）
2. 写探测脚本 `tools/probe_sources.py`：
   - 依次请求每个候选地址，设置超时
   - 判断响应类型（RSS / Atom / JSON / HTML）
   - 对可解析的，输出：来源名、使用的方式、取到的条目数、最新一条的时间
3. 运行探测，把结果整理成一张表
4. 对失败的来源，尝试备选方式（例如 RSS 不行就试网页解析）
5. 仍然不可用的来源，明确标注并给出处理建议（替换 / 移除）

### 输出的表格长这样

| 来源 | 方式 | 状态 | 条目数 | 最新时间 |
|---|---|---|---|---|
| OpenAI | RSS | 可用 | 30 | 2 小时前 |
| 机器之心 | HTML | 可用 | 20 | 5 小时前 |
| 某来源 | 全部失败 | 不可用 | — | — |

### 验证

- 每个保留下来的来源都**真实取到了至少 1 条近期内容**
- 表格里没有猜的、没有“应该能用”的

### 完成标志

我把这张表给你，你确认删改，形成最终的 `sources.yaml`。

### 这一阶段的产出决定什么

- 最终来源清单（写进 `sources.yaml`）
- 每个来源该用哪种抓取方式（决定第 3 阶段写几个适配器）

## 5. 阶段 3：抓取器

**目的**：让程序能稳定地、互不干扰地把各来源内容抓回来。

### 步骤

1. 定义统一的数据结构（字段见设计文档第 6 节）
2. 在 `src/collectors/` 下按来源类型实现适配器：
   - `rss.py`：处理所有 RSS / Atom 来源
   - `html.py`：处理需要解析网页的来源
   - `arxiv.py`：处理 arXiv 的三个分类
   - `hf_papers.py`：处理 Hugging Face Daily Papers
3. 实现抓取调度：并发请求、超时控制、失败重试（2 次）
4. 实现单源失败隔离：一个源失败时记录错误，不影响其他源
5. 为每个适配器写单元测试，使用**固定的样例数据**（不依赖网络，保证测试稳定）

### 验证

- 跑单元测试全部通过（不联网也能过）
- 跑一次真实抓取，看输出条目数与阶段 2 的实测结果是否吻合
- 故意让其中一个来源地址失效，确认其他源仍能正常抓取

### 完成标志

我能对你说：抓取器跑通了，N 个来源抓到了 M 条内容。

## 6. 阶段 4：整理器

**目的**：把抓回来的原始内容，整理成前端能直接用的数据文件。

### 步骤

1. 字段标准化：统一时间格式（UTC）、统一语言标记、补齐缺失字段
2. URL 规范化 + 生成稳定 `id`（用于已读/收藏状态）
3. 去重：按 `id` 去重，同一条内容保留信息最全的一版
4. 合并上一版：从已发布的地址读取旧数据，一起参与合并（对应设计文档第 8.1 节）
5. 排序与截断：按时间倒序，只保留最近 7 天、最多 500 条
6. 写出 `data/feed.json`，包含 `generated_at`、`sources_ok`、`sources_failed` 等元信息
7. 写测试覆盖以上每一步

### 验证

- 单元测试覆盖：字段标准化、URL 规范化、`id` 生成、去重、排序、窗口截断
- 流程测试：完整跑一次，检查生成的数据文件结构正确
- 降级测试：模拟部分来源失败，确认仍能产出且失败列表正确
- 边界测试：全部来源都失败时，**不覆盖已有数据**

### 完成标志

我能对你说：数据管道通了，生成了包含 M 条内容的 feed.json。

## 7. 阶段 5：前端页面

**目的**：把数据变成你能看、能点的界面。

### 步骤

1. 写 `web/index.html`：页面结构（顶栏、筛选标签、信息流列表）
2. 写 `web/style.css`：
   - 信息流样式、已读变淡、收藏高亮
   - 深色 / 浅色主题
   - 响应式布局（手机单列、宽屏更舒适）
3. 写 `web/app.js`：
   - 读取数据文件（带版本参数，防止缓存旧内容）
   - 渲染列表，相对时间显示（悬停看绝对时间）
   - 分类筛选（全部 / 实验室 / 论文 / 中文媒体 / 收藏）
   - 关键词搜索
   - 已读标记（点击后变淡，存本机）
   - 收藏 / 稍后读
   - **页面加载时自动清理过期已读记录，收藏不受影响**（设计文档第 8.5 节）
   - 设置区的“清空已读”“清空收藏”按钮
   - 主题切换并记住选择
   - 手动更新按钮（跳转到定时任务页面）
   - 来源不可用时的降级提示
4. 用一份真实的 `feed.json` 在本地打开页面，逐项验证

### 验证

| 检查项 | 怎么验 |
|---|---|
| 列表渲染 | 打开页面能看到内容，按时间倒序 |
| 跳转原文 | 点击条目在新标签页打开正确地址 |
| 筛选 | 四个分类逐个点，数量随之变化 |
| 搜索 | 输入关键词，列表实时过滤 |
| 已读 | 点开一条后返回，该条变淡；刷新后仍保持 |
| 收藏 | 收藏后出现在“收藏”筛选里 |
| 清理 | 手动制造一条过期已读记录，刷新页面后它被清掉，同时确认收藏还在 |
| 主题 | 切换深色/浅色，刷新后保持 |
| 响应式 | 把浏览器窗口拉到手机宽度，布局正常不溢出 |

### 完成标志

我能对你说：页面做好了，并附上本地打开的地址，你可以自己点一点试试。

## 8. 阶段 6：定时任务与部署

**目的**：让它自动运行，并让手机、平板、电脑都能访问。

### 步骤

1. 写 `.github/workflows/update.yml`：
   - 触发条件：定时（UTC `0 0,5,12 * * *`，对应北京时间 08:00 / 13:00 / 20:00）
   - 触发条件：支持手动运行（供页面上的手动更新按钮使用）
   - 步骤：安装依赖 → 抓取整理 → 生成数据 → 部署静态站点
2. 处理部署所需的账号与仓库（**需要你参与**，见下面说明）
3. 触发一次手动运行，确认整条流水线能通
4. 在电脑浏览器打开站点，确认内容正常
5. 在手机和平板上各打开一次，确认显示正常、能跳转原文
6. 补完 `README.md`：怎么改来源、怎么手动更新、出问题怎么看日志
7. 等一次定时运行实际发生，确认自动化生效

### 关于部署的一个现实问题

当前运行环境**不允许我直接操作项目的 git 版本库**（权限限制）。这不影响代码质量，但影响“怎么把代码送到 GitHub”。可选路径：

- **路径 A**：你把代码文件夹通过 GitHub 网页上传（我会把要传的文件整理好，步骤写得尽量傻瓜）
- **路径 B**：用 Codex 应用自带的版本控制面板提交和推送（如果它对本项目可用）
- **路径 C**：在本地实际使用 git（如果你电脑上装了 Git）

到第 6 阶段我会先试一遍，确认哪条路能走通，再给你最简单的那个。

## 10. 风险与应对

| 风险 | 应对 |
|---|---|
| 中文媒体大面积无稳定源 | 第 2 阶段就暴露，及时调整清单，不拖到最后 |
| 某来源网页改版导致解析失效 | 适配器隔离 + 失败提示；后续按需修一条规则即可 |
| 免费平台定时任务延迟 | 设计阶段已确认可接受；页面显示真实时间 |
| 部署受本地 git 权限限制 | 已准备三条备选路径，第 6 阶段择一通 |
| 免费额度政策变化 | 每天 3 次的用量极低，风险很小；必要时可迁到同类平台 |
